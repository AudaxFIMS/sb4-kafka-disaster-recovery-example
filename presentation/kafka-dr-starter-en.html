Kafka DR Starter

Switching between Kafka clusters with no loss, no duplicates and no failover code in the application

Spring Boot 4 · Spring Cloud Stream 5 · spring-kafka 4 · Java 17+

A Spring Boot starter that makes a Spring Cloud Stream application resilient to the loss of a Kafka cluster. The key idea: the application writes ordinary handlers, while cluster switching, deduplication and restoring the read position are configuration.

The problem

What happens when a Kafka cluster goes down

Consumers stop

The application is bound to one cluster. Moving to the standby means editing config and restarting by hand.

Producers lose messages

The send fails, and the handler often swallows the exception: the record is acknowledged but went nowhere.

Offsets don't match

The standby has offsets of its own. After a switch, records are skipped or processed twice.

Bridges between Kafkas break

A service moving data from one Kafka to another burns its retries in seconds and skips records.

Kafka DR Starter

2

Four typical consequences of losing a cluster. Even with MirrorMaker 2 in place the data is on the standby, but the application does not move there by itself, and the offsets there differ. A separate class of problems is bridge services between Kafkas: when the target Kafka is down the send fails fast, the retries run out, and the record is skipped.

The solution

The application writes ordinary handlers. Choosing the cluster, failing over, deduplicating and restoring the position is the starter's job — driven by configuration.

One YAML: clusters with priorities, consumers, producers. MirrorMaker 2 replicates the data between clusters.

The key message of the deck. The starter does not replace replication — MirrorMaker 2 does that. It answers the question "where do we read and write right now, and how do we avoid losing or duplicating data on the way over".

Three roles. The health checker observes: every interval (5 s by default) it asks each cluster through an AdminClient. The manager decides: it counts consecutive failures and successes, elects the active cluster by priority, honours the failback-after window and persists its state. The executors act: consumer bindings are stopped on the old cluster and started on the new one, and the producer always writes to the active cluster. Replication is MirrorMaker 2 with IdentityReplicationPolicy, so topic names match.

Failover

Failover in five steps — no human involved

01

Probe

describeCluster every 5 s; the deep probe checks partition leaders

02

Threshold

2 failures in a row mark a cluster unhealthy. A send that proves it down — at once

03

Election

The healthy cluster with the highest priority becomes active

04

Switch

Consumers stop on the old cluster, start on the new one, seek by time

05

Failback

After 3 healthy probes, and not before failback-after

The failover state lives in a FailoverStateStore (in-memory or Redis), so the failback-after window survives an application restart.

Kafka DR Starter

5

The numbers are defaults; all are configurable, per cluster group too. The producer can speed things up: when a send proves a cluster unreachable, it is marked unhealthy immediately, without waiting for the probes. failback-after is a time of day before which automatic failback to the primary is not allowed — a night maintenance window, say. For the window to hold across restarts, the state is kept in an external store; the example uses Redis.

Data integrity

No gaps and no duplicates after the switch

Seek by time

On the new cluster reading starts at the timestamp of the last processed record — each consumer has its own.

Idempotency

Records at the switch boundary are dropped by key in an IdempotencyStore: in-memory or your own, Redis for one.

Watermark after commit

The watermark moves only once the offset is committed. With ack.owner: starter the starter commits — handlers need no acknowledgment code.

Kafka DR Starter

6

Three mechanisms work together. Seeking by time removes gaps: offsets differ between clusters, but MirrorMaker keeps record timestamps. The seek is approximate, so the boundary can repeat records; idempotency by message key drops them. Third, the watermark moves only after a real commit — otherwise a failover could jump past records that were never acknowledged.

Kafka DR Starter

7

The main lesson of the development. Every mistake towards "the message is at fault" is a loss for a bridge — the record goes to the DLQ. Every mistake towards "the cluster is at fault" is a needless failover of the whole group, and flapping. So: the message is at fault only for provable properties of the record; the cluster is broken only when it is unreachable or a retriable Kafka error outlasted the retries; everything else is held. Sends are always synchronous: the starter sets sync: true itself. The active-only rule came from a live run: detouring to a standby left records unread.

Kafka DR Starter

8

A group is one logical Kafka with its own primary and standby clusters. An application can have several, and each fails over independently: analytics going down does not touch core. A physical cluster belongs to exactly one group, checked at startup. Producers are addressed by logical name, so moving a topic to another group is a configuration change only. Existing configurations without groups keep working unchanged.

Bridges between Kafkas · depends-on

While the target Kafka is down, records wait instead of being lost

1 · Pause

The consumer's binding is paused while the dependency group has no healthy cluster. No rebalance.

2 · Gate

Records already polled never reach the handler: a nack, redelivered after an interval. No retries spent.

3 · Reclassify

A failed send inside the handler becomes a nack, not an exception. The idempotency mark is released.

max-hold

When the dependency is up yet the record still does not go through, it is held for at most depends-on-max-hold-ms (10 min). Time the group is down does not count.

Kafka DR Starter

9

A bridge is a consumer in one Kafka that writes to another. Without depends-on, the target Kafka going down looks like a handler error: the retries run out in seconds and the record is skipped. With depends-on there are three layers: pause, a gate before the handler, and reclassifying the failure. A nack does not count as a delivery attempt, so the wait can last as long as the outage. max-hold only bounds the case "the group is up but the record is not taken" — a missing ACL, for instance — which would otherwise stall the thread forever. A manual ack-mode is required and checked at startup.

Cons and limitations

What to know up front

Active-passive only

One cluster of a group is read and written; MirrorMaker 2 replicates one way

No exactly-once across Kafkas

A crash between send and commit repeats a record — the IdempotencyStore drops it

Deduplication in memory by default

Marks are lost on restart; production needs a store of its own

A held record stalls its thread

The consumer waits up to max-hold; after that, without a DLQ, the record is skipped

Detection takes time

Probe-driven failover takes interval × threshold; a failing send speeds it up

Missing topic: a ~45 s block

The first send waits for the SCS provisioner — better to create topics before startup

Tied to the stack

Spring Boot 4, SCS 5, Kafka binder; registry errors read in Confluent 8.x shapes

A large configuration surface

Groups, depends-on, ack, batch — it takes discipline and reading the README

Kafka DR Starter

13

An honest list of limitations. The most fundamental is the active-passive model: the starter does no active-active and does not replicate data itself. Exactly-once across different Kafkas is impossible in principle — no transaction spans two clusters — hence the bet on the receiver's idempotency. A held record is a deliberate trade-off, "a visible delay beats a silent loss", bounded by max-hold. The ~45 s block on a missing topic is Spring Cloud Stream's own behaviour and is documented. Schema Registry error recognition was checked against the Confluent 8.2 sources; it is worth re-checking on a major client upgrade.

Summary

When the starter fits, and when it doesn't

A good fit

  • Spring Cloud Stream on Kafka, primary and standby clusters with MirrorMaker 2
  • Automatic failover is needed, without loss or duplicates
  • A service exchanges data between several Kafkas
  • Many teams need DR — done the same way

Not a fit

  • Active-active, or writing to several clusters at once
  • Strict exactly-once across Kafkas
  • Not Spring Cloud Stream: a plain Kafka client or Kafka Streams
  • A single cluster with no standby — the starter adds nothing
