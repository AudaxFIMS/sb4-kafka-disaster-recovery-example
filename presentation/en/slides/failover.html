Failover

Failover in five steps — no human involved

01

Probe

describeCluster every 5 s; the deep probe checks partition leaders

02

Threshold

2 failures in a row mark a cluster unhealthy. A send that proves it down — at once

03

Election

The healthy cluster with the highest priority becomes active

04

Switch

Consumers stop on the old cluster, start on the new one, seek by time

05

Failback

After 3 healthy probes, and not before failback-after

The failover state lives in a FailoverStateStore (in-memory or Redis), so the failback-after window survives an application restart.

Kafka DR Starter

5

The numbers are defaults; all are configurable, per cluster group too. The producer can speed things up: when a send proves a cluster unreachable, it is marked unhealthy immediately, without waiting for the probes. failback-after is a time of day before which automatic failback to the primary is not allowed — a night maintenance window, say. For the window to hold across restarts, the state is kept in an external store; the example uses Redis.
