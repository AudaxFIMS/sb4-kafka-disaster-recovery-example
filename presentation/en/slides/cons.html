Cons and limitations

What to know up front

Active-passive only

One cluster of a group is read and written; MirrorMaker 2 replicates one way

No exactly-once across Kafkas

A crash between send and commit repeats a record — the IdempotencyStore drops it

Deduplication in memory by default

Marks are lost on restart; production needs a store of its own

A held record stalls its thread

The consumer waits up to max-hold; after that, without a DLQ, the record is skipped

Detection takes time

Probe-driven failover takes interval × threshold; a failing send speeds it up

Missing topic: a ~45 s block

The first send waits for the SCS provisioner — better to create topics before startup

Tied to the stack

Spring Boot 4, SCS 5, Kafka binder; registry errors read in Confluent 8.x shapes

A large configuration surface

Groups, depends-on, ack, batch — it takes discipline and reading the README

An honest list of limitations. The most fundamental is the active-passive model: the starter does no active-active and does not replicate data itself. Exactly-once across different Kafkas is impossible in principle — no transaction spans two clusters — hence the bet on the receiver's idempotency. A held record is a deliberate trade-off, "a visible delay beats a silent loss", bounded by max-hold. The ~45 s block on a missing topic is Spring Cloud Stream's own behaviour and is documented. Schema Registry error recognition was checked against the Confluent 8.2 sources; it is worth re-checking on a major client upgrade.
