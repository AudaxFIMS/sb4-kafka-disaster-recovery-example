Kafka DR Starter

Переключение между кластерами Kafka без потерь, без дублей и без кода отказоустойчивости в приложении

Spring Boot 4 · Spring Cloud Stream 5 · spring-kafka 4 · Java 17+

Стартер для Spring Boot, который делает приложение на Spring Cloud Stream устойчивым к падению кластера Kafka. Ключевая идея: приложение пишет обычные обработчики, а переключение кластеров, дедупликация и восстановление позиции чтения задаются конфигурацией.

Проблема

Что происходит, когда кластер Kafka падает

Консьюмеры встают

Приложение привязано к одному кластеру. Переключение на резервный — ручная правка конфигурации и рестарт.

Продюсеры теряют сообщения

Отправка падает, а обработчик часто глотает исключение — запись подтверждена, но никуда не ушла.

Смещения не совпадают

У резервного кластера свои offset'ы. После переключения — пропуск записей или повторная обработка.

Мосты между Kafka рвутся

Сервис, перекладывающий данные из одной Kafka в другую, за секунды тратит ретраи и пропускает записи.

Kafka DR Starter

2

Четыре типичных последствия падения кластера. Важно: даже при настроенном MirrorMaker 2 данные на резервном кластере есть, но приложение само туда не переходит, а смещения там другие. И отдельный класс проблем — сервисы-мосты между разными Kafka: при падении целевой Kafka отправка падает быстро, ретраи кончаются, запись пропускается.

Решение

Приложение пишет обычные обработчики. Выбор кластера, переключение, дедупликацию и восстановление позиции делает стартер — по конфигурации.

Один YAML: кластеры с приоритетами, консьюмеры, продюсеры. Данные между кластерами реплицирует MirrorMaker 2.

Ключевая мысль презентации. Стартер не заменяет репликацию — её делает MirrorMaker 2. Он решает вопрос «куда сейчас читать и писать и как не потерять и не задвоить данные при переходе».

4

Три роли. Health checker наблюдает: раз в интервал (по умолчанию 5 с) спрашивает каждый кластер через AdminClient. Менеджер решает: считает подряд идущие неудачи и успехи, выбирает активный кластер по приоритету, учитывает окно failback-after и сохраняет состояние. Исполнители действуют: binding'и консьюмеров останавливаются на старом кластере и запускаются на новом, продюсер всегда пишет в активный. Репликация — MirrorMaker 2 с IdentityReplicationPolicy, чтобы имена топиков совпадали.

Цифры — значения по умолчанию, все настраиваются, в том числе отдельно для каждой группы кластеров. Продюсер может ускорить переключение: если отправка доказала, что кластер недоступен, он помечается нездоровым сразу, не дожидаясь проб. failback-after — время суток, до которого автоматический возврат на основной кластер запрещён (например, ночное окно обслуживания). Чтобы окно соблюдалось и после рестарта, состояние хранится во внешнем хранилище — в примере это Redis.

Целостность данных

Без пропусков и без дублей после перехода

Seek по времени

На новом кластере чтение начинается с отметки времени последней обработанной записи — у каждого консьюмера своей.

Идемпотентность

Записи на границе перехода отсекаются по ключу в IdempotencyStore: in-memory или своё хранилище, например Redis.

Отметка после коммита

Отметка двигается только после коммита offset'а. С ack.owner: starter стартер коммитит сам — обработчику не нужен код подтверждения.

Kafka DR Starter

6

Три механизма работают вместе. Seek по времени убирает пропуски: offset'ы на кластерах разные, а время записи MirrorMaker сохраняет. Seek приблизителен — на границе возможны повторы, их отсекает идемпотентность по ключу сообщения. Третье — отметка времени двигается только после реального коммита: иначе после failover можно перепрыгнуть записи, которые так и не были подтверждены.

Kafka DR Starter

7

Главный урок разработки. Любая ошибка в сторону «виновато сообщение» для моста означает потерю — запись уходит в DLQ. Любая ошибка в сторону «виноват кластер» — лишний failover всей группы и флаппинг. Поэтому: вина сообщения — только для доказуемых свойств записи; поломка кластера — только когда он недоступен или ретраибельная ошибка Kafka не прошла; всё остальное — запись придерживается. Отправка всегда синхронная: стартер сам выставляет sync: true. Правило «только активный кластер» найдено живым прогоном: обход на резервный кластер оставлял записи непрочитанными.

Kafka DR Starter

8

Группа — это одна логическая Kafka со своими основным и резервными кластерами. В одном приложении их может быть несколько, и каждая переключается независимо: падение analytics не трогает core. Один физический кластер входит только в одну группу — это проверяется на старте. Продюсер адресуется по логическому имени, поэтому перенос топика в другую группу — только изменение конфигурации. Существующие конфигурации без групп продолжают работать без изменений.

Мосты между Kafka · depends-on

Пока целевая Kafka лежит, записи ждут, а не теряются

1 · Пауза

Binding консьюмера на паузе, пока у группы-зависимости нет здорового кластера. Без ребалансировки.

2 · Гейт

Уже вычитанные записи не доходят до обработчика: nack и повтор через интервал. Ретраи не тратятся.

3 · Переклассификация

Сбой отправки внутри обработчика превращается в nack, а не в исключение. Метка идемпотентности снимается.

max-hold

Если зависимость жива, а запись всё равно не проходит, она держится не дольше depends-on-max-hold-ms (10 мин). Время, пока группа лежит, не считается.

Kafka DR Starter

9

Мост — консьюмер в одной Kafka, который пишет в другую. Без depends-on падение целевой Kafka выглядит как ошибка обработчика: ретраи кончаются за секунды, запись пропускается. С depends-on — три слоя: пауза, гейт перед обработчиком и переклассификация сбоя. Nack не считается попыткой доставки, поэтому ожидание может длиться сколько угодно. max-hold ограничивает только случай «группа жива, но запись не берут» — например, нет ACL: иначе такая запись остановила бы поток навсегда. Требование: ручной ack-mode, это проверяется на старте.

Кроме модульных тестов — мутационная проверка: в копию кода намеренно вносились ошибки, и тесты должны были их поймать. Тесты на многопоточность прогонялись многократно. Главная ценность — DR перестаёт быть ответственностью каждой команды, которая пишет консьюмеры. Решения приняты один раз, в стартере, и проверены тестами и живыми прогонами. Изменения, требующие внимания при обновлении, перечислены в README в разделе заметок о миграции.

Минусы и ограничения

О чём важно знать заранее

Только active-passive

Пишем и читаем один кластер группы; репликация — MirrorMaker 2 в одну сторону

Нет exactly-once между Kafka

Сбой между отправкой и коммитом даёт повтор — его отсекает IdempotencyStore

Дедупликация по умолчанию в памяти

После рестарта метки теряются; для прода нужно своё хранилище

Придержанная запись тормозит поток

До max-hold консьюмер не двигается; после — без DLQ запись пропускается

Обнаружение — не мгновенно

Failover по пробам занимает интервал × порог; отправка ускоряет его

Отсутствующий топик: блок ~45 с

Первая отправка ждёт провижнер SCS — топики лучше создавать до старта

Привязка к стеку

Spring Boot 4, SCS 5, Kafka binder; ошибки реестра — по формам Confluent 8.x

Большая поверхность настроек

Группы, depends-on, ack, batch — нужна дисциплина и чтение README

Kafka DR Starter

13

Честный список ограничений. Самое принципиальное — модель active-passive: стартер не делает active-active и не реплицирует данные сам. Exactly-once между разными Kafka невозможен в принципе: нет транзакции, охватывающей два кластера, поэтому ставка на идемпотентность получателя. Придержанная запись — осознанный компромисс «лучше видимая задержка, чем тихая потеря», ограниченный max-hold. Блок примерно 45 секунд на отсутствующем топике — поведение самого Spring Cloud Stream, оно задокументировано. Распознавание ошибок Schema Registry проверено по исходникам Confluent 8.2; при смене мажорной версии клиента это место стоит перепроверить.

Итог

Когда стартер подходит, а когда нет

Подходит

  • Spring Cloud Stream на Kafka, основной и резервный кластеры с MirrorMaker 2
  • Нужен автоматический failover без потерь и дублей
  • Сервис обменивается данными между несколькими Kafka
  • DR нужен многим командам — единообразно

Не подходит

  • Нужен active-active или запись в несколько кластеров сразу
  • Нужен строгий exactly-once между Kafka
  • Не Spring Cloud Stream: чистый Kafka-клиент или Kafka Streams
  • Один кластер без резерва — стартер ничего не добавит
